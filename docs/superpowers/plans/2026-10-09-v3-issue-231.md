# V3 provider errors, timeouts, and retries implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Complete R008, R009 and R167 in [issue #231](https://github.com/EvanProgramming/OpenKyrozen/issues/231).

**Architecture:** Provider-owned errors normalize transport failures. A context-scoped deadline, cancellation event and four-attempt budget are shared by adapters, runtime workers and fallback. Successful response decoding stays outside retry.

**Tech Stack:** Python 3.12/3.13, standard-library contextvars/threading, existing provider SDKs, unittest.

**Spec:** The user-approved issue #231 plan and GitHub source requirements.

## Global constraints

- One issue and one PR; branch Evan/v3-231-provider-errors starts at current main. No merge.
- No new dependency or paid calls. Preserve successful response contracts, model mapping and usage attribution.
- Default deadlines: 90 seconds foreground, 180 child; finite override clamped 1–600 seconds.
- Four transport attempts total, including fallback; disable SDK retries and pass remaining timeout.
- Retry transport, transport timeout, rate limit and server failures only. Authentication may advance to another provider without repeating credentials. Other failures and overall expiry/cancellation are terminal.
- Try fallback candidates in order before repeating transient failures. No replay after a streamed chunk or received response.
- Legacy text boundary retains error rendering and one context-compaction recovery. Tool retry and full tool/process cancellation are out of scope.

## Review focus

- SDK retries must not multiply the shared attempt limit.
- Cancelled/timed-out workers must not start another request or publish late output.
- Structured context errors must still trigger exactly one existing compaction attempt.
- Errors and chained fallback summaries must not display API keys or request bodies.
- Partial streams and successful responses must never be replayed; successful usage remains charged once.
