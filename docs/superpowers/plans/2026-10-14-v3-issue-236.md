# V3 Issue #236 — Execution Receipts and Task Association

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Make each tool receipt identify the exact call and authorized operation, associate tasks only by explicit identity in native execution, and record evidence from typed outcomes.

**Architecture:** Extend the existing `ExecutionReceipt` and shared `AgentRuntime.execute_call()` boundary. Keep `TaskManager` as the owner of Working Plan lifecycle and evidence, `ToolRegistry` as the owner of tool metadata, and `EventStore` as the durable receipt log. Preserve compatibility fields as bounded projections of the immutable tool result.

**Tech Stack:** Python 3.12–3.13, dataclasses, existing JSON-safe `ToolResult`, SQLite-backed event/task stores, `unittest`.

**Spec:** [OpenKyrozen V3 GitHub issue #236](https://github.com/EvanProgramming/OpenKyrozen/issues/236), covering R026–R030 and R066.

## Global Constraints

- No new dependency or paid provider call.
- A missing `task_id` is permitted and cannot infer or advance a plan task.
- A supplied `task_id` must identify a pending/running task in the active Working Plan and current user/workspace/session.
- Execution success comes from `ToolResult`; rendered wording never determines status.
- A receipt or verified effect alone does not satisfy acceptance requirements or complete a task.
- Existing persisted receipts remain readable; audit/event projections remain bounded and redacted.
- Side-effect classification must not grant permissions or make a previously unsafe tool parallel-safe.

## Review Focus

- Native call IDs must survive validation errors, denials, cancellations, and exceptions without executing a rejected call.
- Mutating caller-owned arguments or result snapshots after execution must not alter the receipt or its fingerprint.
- Invalid or stale task identity after an approval wait must prevent execution and leave task state unchanged.
- A pre-existing file or command output that looks successful must not count as verified effect without matching observed state/status.
- Historical receipts and custom/legacy ToolSpec side-effect metadata must remain readable and conservative.

## Caller and Data Map

- `openkyrozen/agent/types.py`: receipt contract, compatibility serialization, and defensive result snapshots.
- `openkyrozen/agent/executor.py`: operation identity, result-to-receipt construction, bounded redaction, persistence/event projections, and legacy adapter.
- `openkyrozen/agent/runtime.py`: native `execute_call()` call/task identity, schema and approval failures, and task eligibility rechecks.
- `openkyrozen/app/bootstrap.py`: scope the default TaskManager to the initial session and workspace instead of its unscoped compatibility defaults.
- `openkyrozen/tasks/engine.py` and `openkyrozen/tasks/runtime.py`: explicit evidence association and active Working Plan checks; legacy inference remains available only to the legacy execution adapter.
- `openkyrozen/agent/subagent_runtime.py`, `openkyrozen/learning/evolution.py`, `openkyrozen/tools/catalog.py`, and `openkyrozen/tools/manifest.py`: typed verification/acceptance inputs and refined metadata.
- `tests/test_tool_results.py`, `tests/test_working_plans.py`, `tests/test_approval_request.py`, `tests/test_task_consistency.py`, and new focused receipt tests: regressions for receipt identity, task scope, verification, projections, and compatibility.
- `docs/security.md`, `docs/tasks-and-automation.md`, and `docs/architecture.md`: document the receipt and task-association boundary where current guidance discusses it.
